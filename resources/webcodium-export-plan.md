# WebCodium export plan - naive → SCSS → Kit-basis

`VISION.md`'s 3rd Principle states the mandate in one line: *"WebCodium - a markup exporter driven by user-defined Export Profiles. First targets are HTML, CSS, Svelte, and SCSS... WebCodium understands variants as discrete or a dynamic thing."* This doc is the elaboration - the concrete mechanics behind that sentence, phased.

Phases 1, 2, and 3 (v1 scope) are built. Phase 3.1 (below) is roadmap, not implementation.

---

## Phase 1 - naive per-node export (shipped)

`export_html_css` (`plugins/webcodium/src/lib.rs`, translation split across `tree.rs`/`css.rs`/`html.rs` as of the Phase 2 restructure) walks Charter's resolved `UiNode` tree and emits one CSS class per **rendered node instance** - `.k10-39`, `.k10-40`, ... - with literal, already-resolved values (`width: 900px`, `background: oklab(...)`) baked directly into each rule. Output is a single HTML file with the CSS inlined in a `<style>` block - single-file to sidestep the two-file download quirk documented in `download.ts` (see `CLAUDE.md`'s `plugins/webcodium/` section).

This is a direct, unopinionated dump of whatever Charter resolved for the exported view(s). It has no concept of kits, axes, or variants - a node's class exists because that node was rendered, not because it represents a reusable design unit. It's the correct minimal v1 (proves the `kit10_get_interpreter_output` pipeline end to end), but it is explicitly **not** the intended end state - later phases replace this translation strategy, not just add options on top of it.

---

## Phase 2 - SCSS by default (shipped)

SCSS is a strict superset of CSS - anything emitted as SCSS always transpiles losslessly to plain CSS, so switching the default output target costs nothing functionally. What it buys is brevity: SCSS's nesting syntax lets sibling/child relationships collapse instead of repeating fully-qualified selectors, which matters more as Phase 3's nested selectors (see below) make the output tree-shaped rather than flat.

Shipped scope, as implemented (`css::render_scss`, `plugins/webcodium/src/css.rs`):
- Output format changed from plain flat CSS to nested SCSS - a child node's rule is written inside its parent's block, mirroring the same parent/child recursion `html::render_html` already used for `<div>` nesting (only `Box` nodes recurse into children, matching exactly).
- Deliberately plain descendant nesting - no `&`, no Sass variables, no mixins - which makes the output simultaneously valid real Sass (renameable straight to a `.scss` file and compiled) AND valid native CSS (the CSS Nesting spec, Baseline across evergreen browsers since 2023). This is what let it ship inline, unchanged from Phase 1's decision: still a single exported HTML file with the stylesheet inlined in `<style>`, still renders correctly in a browser as-is.
- No axis/variant awareness - that's Phase 3. This phase was a pure syntax-target swap on top of Phase 1's existing per-node translation, exactly as scoped below (not a file-count change, no new export capability/manifest entry - `export_html_css`'s external contract is unchanged).

**Two correctness follow-ups landed the same day, orthogonal to the phase numbering above** - full detail in `CLAUDE.md`'s `plugins/webcodium/` section, not repeated here: `css.rs` now emits the full `BoxExtra`/`BoxData` layout surface (align/justify/flex-grow-shrink-basis/min-max-size/grid), closing a real divergence between Vellum's in-editor rendering and the browser export; and every export is now prefixed with a small first-party CSS reset (`css::BASELINE_RESET`) fixing a `<p>`-margin leak that neither `normalize.css` nor `the-new-css-reset` would have solved cleanly.

## Phase 3 - Kit-basis export (v1 shipped 2026-07-27)

The larger architectural shift: export one class per **Kit** (e.g. `.button`), not one per rendered node instance. This required WebCodium to reason about the axis/kit model itself for the first time - every prior phase only ever consumed Charter's already-resolved, axis-blind output.

Decisions made (were open questions when this doc was first written):

1. **Axis exclusion is per-Kit**, not per-project Export Profile - `axes_consumed.excluded_from_export: boolean` (default `false`), scoped to the exact (kit, axis) join row. An excluded axis collapses to a single base rule using the axis's own `default_value` (or its lowest-`priority_index` value if unset) - no conditioned rule emitted for it at all. Set via the Axes panel's per-axis context menu (the "Expose"/"Include in Export" toggle on `Axis.svelte`).

2. **Static vs. dynamic classification is an explicit per-axis flag**, not inferred from axis semantics - `axes.variant_kind: 'static' | 'dynamic'` (default `'static'`), global to the axis (not per-value). Set via the same Axes panel context menu ("Set Dynamic"/"Set Static").
   - **Static** values produce a BEM modifier class: `.button--secondary`.
   - **Dynamic** values map through a small recognized-name table to a real CSS pseudo-class (`hover`→`:hover`, `focus`→`:focus`, `focus-within`, `focus-visible`, `active`, `visited`, `checked`, `disabled`), falling back to a `.is-{value}` JS-toggle-style compound class for any unrecognized name. See `plugins/webcodium/src/variants.rs`'s `dynamic_selector_suffix`.

3. **Nesting homology** reuses the existing `composition_field_keys`/`viewRefs` graph walk exactly as planned - no new graph-walking mechanism. **Nesting-vs-modifier interaction, resolved decisively:** a child Kit's own modifiers always attach to the child's own base class, nested only at the base level under its ancestor - `.button .card--variant`, never `.button--variant .card`. Each Kit owns its own modifier vocabulary regardless of which parent happens to contain it.

### The unresolved-shape gap, and how it was closed

Every phase before this one only consumed Charter's already-resolved output (`kit10_get_interpreter_output`'s flat, axis-blind `UiNode[]`). Kit-basis export needed the *unresolved* shape too. This landed as:
- A new resolver function, `manager/src/resolve/export-shape.ts`'s `fetchKitExportShapes` - reuses `resolve.ts`'s `fetchLayerData` query shape but skips `matchLayers`' collapse-to-winner step, returning every layer's full condition set/entries per Kit, plus axis metadata (`variantKind`, `excludedFromExport`, ordered `values`, `defaultValue`).
- A new host-fn, `kit10_get_kit_export_shape` (gated via `capabilities.hostFns`, alongside the pre-existing `kit10_get_interpreter_output` - both manifests, `plugins-bootstrap.ts` and `plugin-catalogue.ts`, updated in lockstep). WebCodium calls it once per export with the distinct Kit ids actually present in the viewport (`tree::distinct_kit_ids`).
- A third parallel array, `node_kit_ids` (alongside the existing `node_view_ids`), threaded from Charter's `build_viewport` through `OnResolveResult`/`OnSelectionChangeResult`, `manager.svelte.ts`, and `interpreter-output.ts` - names the highest-priority composed Kit for each rendered node (mirrors `merge_kits`' own "later kit wins" convention). This is what lets WebCodium know *which* Kit a given node came from, since a Kit has no subtree of its own in Charter's merged output.

### v1 scope cut: properties whose meaning depends on sibling/parent context are skipped, not guessed

WebCodium cannot safely re-derive Charter's *compiled* CSS output from raw `render_entries` strings when that compilation genuinely needs sibling/parent layout context it doesn't have - concretely, `resize`'s `fill`/`hug` keywords on `width`/`height` (`compile_resize`'s flex-grow/shrink/basis math depends on the parent's own main axis). Re-deriving these risks silently diverging from what Charter actually renders in-editor. `plugins/webcodium/src/variants.rs` skips these with an explicit `/* unsupported dynamic-compiled property: X */` comment in the output rather than guessing.

`arrange` (Stack/Cluster/Split/Center/Grid) is **not** in that scope-cut category, despite also being Charter's own compiled preset - see the dedicated note below; it's fully synthesized, not skipped. `plugins/webcodium/src/variants.rs`'s diffable whitelist: `background`, `color`, `font-family`, `font-size`, `font-weight`, `padding`, `border` (see below), `border-radius`, `opacity`, `gap`, a literal - non-`fill`/`hug` - `width`/`height`, `grid-template-columns`/`-rows`, and the direct-enum `flex-direction`/`align-items`/`justify-content`/`flex-wrap`/`text-align`/`text-decoration`/`line-height`. Also v1-scoped: only `literal`/`discrete` axis values are matched (range axes are disabled project-wide, see `resources/layer-authoring.md`). Multi-axis conditions ARE supported: a layer conditioned on two or more non-excluded axes together produces one combined `VariantRule` - a compound selector chaining one axis-prefixed BEM fragment per condition (`.button.button--plan-elite.button--theme-dark`), always static regardless of any contributing axis's own `variant_kind` ("assume everything is static for now" - mixing several axes' dynamic pseudo-classes into one compound selector stays out of scope). See `plugins/webcodium/src/variants.rs`'s module doc comment.

**Static/`.is-` variant rules only actually apply to an exported element because of a second, separate mechanism**: `kit10_get_view_axis_args` (a new host fn, mirroring `kit10_get_kit_export_shape`'s per-Kit-shape pattern but per-view-instance) tells WebCodium which axis value(s) each exported node's own view resolved to, so `lib.rs`'s `compute_instance_modifier_classes` can append the matching modifier class(es) to that instance's `class=""` attribute via `variants::rule_matches_args`. Before this, EVERY static/`.is-` variant rule ever exported - single-axis included - was unreachable dead CSS: `html.rs` only ever wrote the base Kit class onto an element, nothing ever put a modifier class there. Real dynamic pseudo-classes (`:hover`, `:focus`) were and still are unaffected, since the browser applies those from actual user interaction with no class needed.

**`display` is deliberately never diffed from a raw property, and is computed instead (fixed 2026-07-27, real bug in the initial v1 ship).** Charter only ever writes a literal `display` render entry via the rarely-touched "Advanced flex" escape hatch (`box_categories()`'s `arrangeKeys.advanced`) - the overwhelmingly common case (a Kit authored through Stack/Cluster/Split/Center/Grid, never touching Advanced) never stores `display` at all; Charter computes it purely from whether a grid-template is present. The initial Phase 3 ship missed this: it treated `flex-direction` as diffable (correctly) but never synthesized a matching `display: flex`, so a real, exported Kit-basis box could carry `flex-direction` with no `display` at all - CSS silently no-ops `flex-direction` without a flex/inline-flex display mode, so the whole arrangement broke in the browser while looking fine in-editor. Fixed by `variants.rs::box_display_declaration`, which mirrors `css.rs::node_props`'s own `is_grid` check (`grid-template-columns`/`-rows` non-empty → `display: grid`, else `display: flex`) and is always injected as the base rule's first declaration for a Box-primitive Kit node (never for Text/Img). `synthesize_base_declarations` takes an `is_box: bool` for exactly this reason.

**`border` and `border-width` are two independent raw kit properties that must combine into ONE atomic shorthand, never diffed separately (fixed 2026-07-27, same session, same class of bug).** `box_categories()`'s `border` field is color-only (`FieldDef::new("border", None).with_input_type("color")`); the actual visible border needs a width and a style too, both of which Charter computes rather than stores - `extract_paint_props` defaults `border_width` to `1.0` whenever a border color is set but no explicit `border-width` is, and the style is always hardcoded `solid` (`css.rs::node_props`'s own `border: {width}px solid {color};`). The initial ship diffed `border` (a bare color) and `border-width` (a bare px number) as two ordinary independent properties - `border: <color>;` alone is syntactically valid CSS, but it leaves `border-style` at its `none` initial value, so **the border never actually rendered at all**, while looking correct in the editor. Fixed by `variants.rs::synthesize_border`, called from inside `resolve_properties` itself (so it applies identically to the base and every variant's resolved map): it merges the two raw keys into one atomic `border` value (`"{width}px solid {color}"`, width defaulting to `1` when unset, entry removed entirely when no border color is set or it's `"none"`) before the normal diffable-property pipeline ever sees them. `border-width` was removed from `DIFFABLE_PROPERTIES` - it never survives as its own key by the time that list is consulted. A variant that overrides only the border color still recomputes the *whole* shorthand (carrying the base's width forward), since border is diffed as one atomic string like every other property.

**`arrange` (Stack/Cluster/Split/Center/Grid) is fully synthesized, not skipped as an unsupported compiled property (fixed 2026-07-27, same session - reported live: "split is not working").** The initial ship lumped `arrange` in with `resize`'s genuinely-unfixable `fill`/`hug` case, but `compile_arrange`/`resolve_flex_direction` (`plugins/charter/src/lib.rs`) need nothing from sibling/parent layout context - they're a pure function of the Kit's own raw properties plus a constant (`grid-cell-min`'s default of `160`). Since a Kit authored via the high-level Split/Cluster/Center presets (the overwhelmingly common authoring path) only ever stores the single `arrange` property, never the `flex-direction`/`justify-content`/`align-items`/`flex-wrap` it implies, treating `arrange` as unsupported meant those Kits exported with **none of their actual layout** - Split's `justify-content: space-between` and `align-items: center` simply never appeared, so the export looked flattened/broken while the editor rendered it correctly. `variants.rs::synthesize_arrange` now replicates `compile_arrange` exactly (same default-only-when-unset rule per arrange kind, same `resolve_flex_direction` row/column defaulting, same `TrackSize::AutoFit(cell_min)` → `repeat(auto-fit, minmax({cell_min}px, 1fr))` for Grid), called from `resolve_properties` and gated on `is_box` (a Text-primitive Kit never has these properties to begin with). `align-items`/`justify-content`/`flex-wrap` were added to `DIFFABLE_PROPERTIES` since they're now legitimately synthesized values.

### Phase 3.1 (not built) - the real fix for the scope cut

The technically correct fix is a small new Charter `plugin_fn` (e.g. `translate_properties`) that runs an arbitrary property map through Charter's own existing `build_box_node`/`build_text_node` compiler, so the host can round-trip each variant's raw property map through *real* Charter compilation before handing WebCodium a genuinely Charter-translated `UiNode` to run through the unchanged `css.rs::node_props`. This needs a Charter change and a host-orchestrated multi-plugin call (host → Charter → WebCodium), so it's deferred - the v1 literal-property whitelist already covers the large majority of real Kit variance (colors, sizes, text) without it.

## Img support (shipped 2026-07-27)

Every phase above was explicitly Box/Text only, Img skipped entirely - `ImageSource::Bytes`/`Ref` both needed a decision (data URI vs. asset pipeline) the plan deferred. Resolved in favor of the simplest correct option: **if the asset resolves to a real URL, use it; otherwise skip, still no data-URI embedding.**

- **New host-fn, `kit10_get_asset_links`** - resolves a batch of Img `src` asset ids (`ImageSource::Ref(id)`) to their `assets.link` column (a real URL - a bundled static path today, a future cloud-hosted link later). Mirrors `kit10_get_kit_export_shape`'s batching pattern exactly: `lib.rs`'s `distinct_img_asset_ids` collects every distinct id actually referenced in the viewport before the one host-fn call, same dedup shape as `tree::distinct_kit_ids`. An asset with no `link` (bytes-only, never given one) is simply absent from the response map - the plugin treats a missing entry as "no known URL," never a hard failure.
- **`tree::resolved_img_src`** is the single shared lookup (`ImageSource::Ref(id)` → `asset_links.get(id)`) both `css.rs` and `html.rs` consult, so the two can never disagree about which Img nodes actually render.
- **`html.rs`** emits `<img class="..." src="..." alt="">` when a link resolves, nothing otherwise (unchanged fallback for `None`/`Bytes` sources, or a `Ref` with no known link).
- **`css.rs`**'s `node_props` gained an `Img` match arm gated on `has_resolved_img_src` (no rule at all when false, matching html.rs emitting no tag): `width`/`height` (when not `Auto`), `object-fit` (`fit` is already a real CSS keyword - `cover`/`contain`/`fill`), and `object-position` (the wire's `0..1` fractions converted to CSS's `N% N%` syntax). `background`/`border`/`padding` are **not** emitted for Img - `ImgData`'s actual wire struct has no fields for them at all (the Render panel's `image_categories()` declares those fields, but Charter's `build_img_node` never reads or wires them through - a separate, pre-existing gap, not addressed here).
- **Img nodes never route through the Kit-basis `variants.rs` path**, even when composed via a Kit (a real `node_kit_ids[i]`) - that machinery synthesizes CSS from Box/Text's paint+layout vocabulary (`background`, `flex-direction`, ...) and has no concept of `src`/`fit`/`object-position` at all; routing an Img through it would misfile those three as "unsupported compiled properties." Img still gets the correct 3-tier class name from `tree::resolve_class_name` (Kit name / `"img"` / positional) independent of this - only the CSS-*content* decision bypasses Kit-basis, not the class-*naming* decision.

## Font support - real `@font-face` links (shipped 2026-07-27)

Before this, an exported Text node's `font-family: "Inter";` declaration had nothing backing it - the browser silently substituted a local or generic font, since the export never shipped (or linked to) the actual font file. Same "extrapolate a real URL, no hardcoding" principle as Img support, applied to fonts: **no font provider or URL is ever hardcoded in WebCodium - every link comes from Fontavious's own catalogue, routed through the host.**

- **New host-fn, `kit10_get_font_links`** - resolves a batch of `(family, weight, style)` requests to the real URL Fontavious's `variant_url` export would resolve each to. Unlike `kit10_get_asset_links` (a manager-side DB lookup), this one is implemented by the HOST calling *another plugin* (`callUtilityPlugin('fontavious', 'variant_url', ...)`) from inside a host-fn handler - safe because `callUtilityPlugin` queues per-plugin-name (`utilityQueues`, keyed by e.g. `'fontavious'`), never the caller's own queue entry (`'webcodium'`) or the interpreter's `pluginQueue`, so this cannot deadlock against the very `export_html_css` call it's serving. Calls the SAME `variant_url` export the editor's own font-fetch scan (`Editor.svelte`'s `loadVariant`) already uses, so an export can never disagree with what the live editor would actually load.
- **`lib.rs`'s `distinct_font_requests`** scans `Text` nodes for distinct `(font_family, font_weight, font_style)` triples (first-appearance dedup, same shape as `distinct_img_asset_ids`/`tree::distinct_kit_ids`). Reads straight off the already-resolved `TextData` fields - `build_viewport` runs `snap_text_weights` (Charter's `resolve_font_weight`) before WebCodium ever sees the data, so the wire's `font_weight` already IS the post-snapping decision; no separate lookup needed to match what Charter actually rendered.
- **`css::render_font_faces`** emits one `@font-face` block per resolved link (`font-family`/`font-weight`/`font-style`/`src: url("...") format("woff2")`) - always `woff2`, since that's the only format Fontavious ever fetches. A request with no resolved link (a catalogue miss, an uncatalogued family) is simply absent from the response and skipped - the plain `font-family` declaration elsewhere in the stylesheet still stands, falling back exactly like it did before this feature existed.
- `@font-face` blocks are prepended to the stylesheet ahead of `css::BASELINE_RESET` and the rest of the generated rules (position doesn't affect CSS validity, just reads more naturally at the top).

## Viewport/export parity audit - 7 fixes (shipped 2026-07-27)

A full field-by-field audit comparing Vellum's live rendering against both of WebCodium's rendering paths (Path A - `css.rs::node_props`, the fully-compiled `UiNode`; Path B - `variants.rs`, raw uncompiled kit properties) found 7 concrete discrepancies, all fixed the same session:

1. **Text paint properties missing from Path A.** `extract_paint_props` (Charter) is shared by `build_box_node`/`build_text_node` - a Text node can carry `padding`/`background`/`border`/`border-radius`/`opacity` (a highlighted/pill label), and Vellum draws them for Text exactly like Box. `css.rs::node_props`'s `Text` arm emitted none of them. Fixed by factoring a shared `paint_props(...)` helper in `css.rs`, called from both the `Box` and `Text` match arms.

2. **`line-height` multiplier mis-formatted in Path B.** Charter's `compile_line_height` treats a bare-number raw value as a *multiplier of font-size* (`"1.5"` → `font_size * 1.5`px); `variants.rs`'s generic `as_px_if_bare_number` formatter read the same `"1.5"` as a literal `1.5px` - catastrophically cramped/overlapping lines. Fixed by `variants.rs::synthesize_line_height`, replicating `compile_line_height`'s exact dual-read (px-suffixed = absolute, bare number = multiplier, unset = the ~1.5x→1.1x ratio ramp), called from `resolve_properties` for Text kits only (mirrors `build_text_node` being the only caller of `compile_line_height` in Charter - a Box never gets this synthesized).

3. **`font-weight` keyword vs. numeric divergence in Path B.** `build_text_node` only parses a numeric string (`parse_px(...) as u16`, falling back to 400/normal for anything else, e.g. `"bold"`); `variants.rs`'s generic passthrough formatted `"bold"` verbatim, which the browser renders as real bold (700) where Vellum/Path A show normal (400) for the identical data. Fixed by giving `"font-weight"` its own `format_value` case (`variants.rs::format_font_weight`) mirroring the numeric-parse-or-400 fallback exactly. Charter's further `resolve_font_weight` family-weight-snapping (Fontavious facts) is deliberately not replicated - WebCodium's export pipeline has no family-facts input.

4. **Grid line-placement properties missing from Path B's whitelist.** `grid-auto-rows`/`grid-auto-columns`/`grid-column`/`grid-row` (the Grid tab's "Custom tracks" escape hatch) were absent from `DIFFABLE_PROPERTIES`, so a Kit-basis Grid item using them got an inert "unsupported" comment even though Path A already emits all four unconditionally. Fixed by adding all four - their raw stored values are already valid CSS syntax as-is, no new formatter needed.

5. **Item-level flex properties missing from Path B's whitelist.** `flex-grow`/`flex-shrink`/`align-self` are no longer panel-exposed (superseded by the Fixed/Hug/Fill resize control) but Charter still parses them as a literal raw-property escape hatch for legacy/imported data. Added to `DIFFABLE_PROPERTIES` alongside fix 4. **`flex-basis` is deliberately excluded** - unlike the other three, Charter never reads a raw `"flex-basis"` kit property at all (`build_box_node` hardcodes it to `None` until `compile_resize`'s Fill mode sets it to `Px(0.0)` afterward); there is no raw property for Path B to diff, so whitelisting it would let a stray literal leak into the export as a declaration Charter itself never honors - the opposite of parity.

6. **Color value formatting divergence (named colors, unparseable fallback) in Path B.** Charter's `parse_color` only recognizes `oklch()`/`oklab()`/`transparent`/hex/`rgb()`/`hsl()`; anything else (a CSS named color like `"red"`) is unparseable and becomes a visible magenta marker (`unparseable_marker()`, `OklabColor::from_srgb([1.0, 0.0, 1.0, 1.0])`) - deliberate, never silent black. Path A always reads the already-resolved (magenta-if-unparseable) color; Path B's generic passthrough let `"red"` render as real red. Fixed by `variants.rs::is_recognized_color` (a minimal prefix/keyword check mirroring `parse_color`'s own dispatch order, not the full conversion math) gating `"background"`/`"color"` in `format_value` and the color half of `synthesize_border`'s shorthand - an unrecognized value formats as `unparseable_color_marker()`, computed via the SAME `kit10_scene::OklabColor::from_srgb` conversion and `css::oklab_css` formatting Path A uses (made `pub(crate)`), not a hand-copied literal that could drift.

7. **Absolute-positioned (pinned) views were unreachable in the export entirely.** A view pinned via `hints.vellum.position` is wrapped by Charter in a structural `absolute_box` node (`BoxExtra.position: NodePosition::Absolute{x,y}`) whose only child is the view's own real content, one hop down. `tree::resolve_export_roots` selects roots by `node_view_ids` - the wrapper's id is always `""`, so it never blocks its child from becoming a root directly, and the wrapper itself (carrying the position) was never visited by any render function; a pinned view exported as a plain, arbitrarily-ordered flow element, its canvas position silently dropped. Fixed by `tree::root_position(nodes, root)` (looks up whether `root`'s own parent is exactly that wrapper shape) called once per root in `css::render_scss`/`html::render_html`. **The position rule uses its own always-unique selector (`tree::class_name(i)`, the plain positional fallback), never the root's own resolved class** - a Kit-basis root's own class (`resolve_class_name` tier 1) can be shared with every other, unpositioned instance of that same Kit elsewhere in the tree, and world-space `(x, y)` is per-view-instance data, not per-Kit; folding it into the shared rule would leak one instance's position onto every other instance of the same Kit. The rendered element carries both classes (e.g. `class="button k10-5"`).

**Follow-up caught immediately after shipping fix 7 (same session, reported live: "why did you put the artboard coordinates"): the raw `(x, y)` root_position returns is a coordinate in the EDITOR CANVAS's own world space, not a meaningful page pixel position.** A designer can drag a pinned view anywhere on Vellum's effectively infinite canvas - emitting that value verbatim as `left`/`top` against the exported page's initial containing block would strand content however far from the origin the canvas coordinates happen to sprawl (a view pinned at canvas `(3000, 1400)` would export a page sized to fit that, not a normal document). Fixed by `tree::normalized_root_positions(nodes, roots)`: computes the raw position for every pinned root in the export, then offsets each by the minimum `x`/`y` across all of them, so a single pinned root always normalizes to exactly `(0, 0)` and multiple pinned roots keep their RELATIVE arrangement to each other (what a design that deliberately overlaps/staggers pinned views actually needs preserved) while the page itself starts near the origin like a real document. Both `css::render_scss` and `html::render_html` consult this same normalized map (not the raw per-root `root_position` lookup) so "is this root positioned" and "where" never disagree between the two.

## Multi-Kit Composition Export (shipped 2026-07-31)

Prerequisite discovery: WebCodium's Kit-basis export (Path B, `variants.rs`) had **no representation of multi-kit composition at all**, not just an unhandled edge case. Charter's `kit_id_for(kits) -> String` (`plugins/charter/src/lib.rs`) collapses a rendered node to a single "winning" kit id (`kits.last()`, the highest-priority composed kit) before WebCodium ever sees the data - `node_kit_ids` is singular by construction. A view composing two kits (e.g. a `Layout` kit and a `Button` kit, or the `Density`/`Priority` example below) only ever got ONE class and ONE base rule in the export; the lower-priority kit's own properties simply never appeared anywhere in the stylesheet, contested or not.

This surfaced because of a separate resolver fix earlier the same session: `flattenKitResults`/Charter's `merge_kits` used to let whichever kit was composed last win a property outright, with zero regard for layer specificity (CLAUDE.md's `flattenKitResults` entry has the full rationale). Making that specificity-aware (highest `conditionCount` wins regardless of kit order, kit order only breaks a tie) reopened the question of whether CSS export could represent the same rule - CSS has no native way to say "the kit with more conditions wins regardless of stylesheet order," and two same-specificity single-class selectors are decided by source order alone, which can't simultaneously satisfy two views composing the same two kits in opposite priority order.

**Phase A - `kit10_get_view_compositions`.** New host fn, batched like `kit10_get_asset_links`/`kit10_get_font_links`, backed by `manager/src/resolve/export-shape.ts`'s `fetchViewCompositions` (a plain `compositions` table query, `{viewId, kitId, priorityIndex}[]`, ordered ascending). This is the only way WebCodium learns a view composes more than one kit at all, and in what order - `node_kit_ids` never carries this.

**Phase B - multi-kit class/base-rule emission.** `tree::resolve_class_names` (plural, new) returns the existing 3-tier `resolve_class_name` as its first entry, plus one class per OTHER kit the node's view composes (`view_compositions`, skipping the primary), in composition-priority order. For a single-kit view (every case before this shipped) this is byte-identical to the old single-class output. `css::render_scss_node` gained a matching secondary-kit loop, right after the primary kit's own base/variant rule emission: for every OTHER composed kit not yet in `emitted_kits`, synthesize and emit its own base + variant rules under its own class, exactly the same call shape the primary kit already used (`variants::synthesize_base_declarations_with_tokens`, `kit_variant_rules.get(kid)`). `synthesize_all_variant_rules` and `compute_instance_modifier_classes` (`lib.rs`) both gained a second pass over `view_compositions` alongside their existing primary-kit pass, using `tree::view_primitive_is_box` (new - view id → is-Box, absent for Img views) to know a secondary kit's `is_box` without needing it to ever be some node's own primary.

**Phase C/D - contested-property detection and disambiguation.** `variants::resolve_condition_counts` mirrors `resolve_properties_with_tokens`'s exact matching/sorting (filter by args, sort ascending by condition count, later overwrites earlier) but tracks only the winning layer's own condition count per property - the raw, undecorated specificity signal `flattenKitResults`/`merge_kits` compare, never WebCodium's own derived/synthesized properties (`synthesize_arrange`/`synthesize_border`/`synthesize_resize`), which have no resolve.ts analog. `variants::synthesize_contested_rules(kit_ids, ...)` finds every property 2+ of a view's composed kits declare and picks the winner exactly the way the resolver does: highest condition count wins outright regardless of kit order; a tie falls back to kit order (later/higher-priority kit wins, matching the pre-existing plain-overwrite behavior for the common case).

**The refinement a bare kit-class compound selector alone can't handle:** two views composing the identical two kits in *opposite* priority order can resolve to *different* winners for the same contested property, but `.density.priority {}` as a selector can't tell the two views apart - class order in an element's `class=""` attribute doesn't affect CSS matching at all. Fixed by `tree::composition_signature_class(kit_ids)` - a short, deterministic, ORDER-SENSITIVE hash (`std::collections::hash_map::DefaultHasher` over the ordered kit-id slice, no crypto needed for a same-process disambiguation label) appended to `resolve_class_names`' output whenever a view composes 2+ kits. Two views with the identical ordered composition hash identically (safely sharing one disambiguating rule, same dedup discipline as `kit_names`/`asset_links` being computed once per distinct value); two views with reversed order hash differently, so their rules select genuinely different node subsets instead of contesting one shared selector position. Each `ContestedRule`'s selector chains every one of the view's composed-kit classes plus this signature class (`lib.rs`'s `render_contested_rules_css`, appended flat at the very end of the generated stylesheet) - enough extra class tokens that real CSS specificity (one point per class) reliably exceeds any single-kit base rule, so the correct winner applies regardless of where in the stylesheet either rule happens to sit.

Scope cut, deliberate: cross-kit tie-breaking compares condition *count* only, not the full `[count, ...axisPriorities]` specificity `matchLayers` uses within one kit - two different kits tying on condition count fall back to kit order even if their axis priorities would tie-break differently within a single kit (same scope cut `flattenKitResults` itself takes, see CLAUDE.md).

## Squircle export fallback - proportional area-match convention (shipped 2026-08-04)

WebCodium was two `kit10-scene` tags behind (`v0.2.0`) when Vellum/Charter shipped squircle corner
rendering (`v0.2.2`), so it had no visibility into `BoxData`/`TextData.squircle` at all until this
pass bumped `plugins/webcodium/Cargo.toml`'s tag.

**The question this section answers: what should a squircle box's `border-radius` export as, given
real CSS has no broadly-shipped way to render a true superellipse corner?** `corner-shape:
superellipse()` is not confirmed to be broadly stable in shipping browsers; `clip-path:
path("...")` is broadly supported but only clips the element's silhouette - it does not draw a
matching border stroke or shadow along the new edge, so a bordered/shadowed squircle box would need
extra per-node markup (an SVG overlay, or an offset pseudo-element faking a stroke) just to look
right. Both were scoped OUT of this pass: the whole point of a fallback is staying simple, and
neither is simple.

**What shipped instead: a proportionally-scaled circular `border-radius`, not the literal value.**
"Same px number" is not actually the closest visual match - a circular corner at radius `r` removes
a FIXED ~21.5% of its own `r×r` corner-square area (`1 - π/4`), while the shipped `n=4` squircle
removes a FIXED ~7.3% (`1 - ∫₀¹(1-x⁴)^0.25 dx`), both ratios independent of `r` (confirmed
interactively with an area-vs-diagonal-reach comparison before committing to this metric - the two
metrics pull in OPPOSITE directions for the fallback radius, and area-removed weight was the one
chosen as matching perceived "amount of rounding" more closely than diagonal reach/sharpness would).
`SQUIRCLE_AREA_MATCH_SCALE ≈ 0.58306` (`css.rs`, `pub(crate)`) is the radius multiplier that makes
the fallback circle remove the same ABSOLUTE corner area the squircle did - computed via numeric
integration, not hand-typed, and guarded by a test (`squircle_area_match_scale_is_self_consistent`)
that re-derives it the same way and fails loudly on drift.

**Both export paths apply it, from the same shared constant:**
- **Path A** (`css.rs::paint_props`) reads `BoxData`/`TextData.squircle` directly (now visible
  post-version-bump) and scales `corner_radius` before emitting `border-radius`.
- **Path B** (`variants.rs`) has no compiled `squircle` field to read - only the raw kit property
  `border-radius-squircle` (Charter's `RadiusKeys` companion, a `"1"`/absent boolean-string). New
  `synthesize_radius` consumes that raw property and scales `border-radius` in place, mirroring
  `synthesize_border`'s existing "merge two raw properties into one atomic declaration" shape -
  added to `DIFFABLE_PROPERTIES`'s synthesis pass (`synthesize_border` -> `synthesize_radius` ->
  `synthesize_resize`), not the passthrough whitelist itself, since `border-radius-squircle` must
  never reach `format_value` as its own (non-numeric) declaration.

**Named, accepted coupling risk**: `0.58306` is mathematically derived FROM `SQUIRCLE_N = 4` in
`taf_can_do/src/render/shader.wgsl`. There is no automated cross-language link between a WGSL
shader constant and a Rust plugin constant in a different crate - if `SQUIRCLE_N` is ever retuned,
this scale factor must be manually recomputed and the self-consistency test's expected value
updated with it. A code comment in both locations points at the other; nothing enforces it further.

Verification: `plugins/webcodium/src/tree.rs`/`variants.rs`/`lib.rs` gained targeted unit + end-to-end tests, including the exact reported scenario (a `Density` kit with a `theme=dark`-conditioned layer composed below an unconditioned `Priority` kit; reversing the two kits' composition order flips both the winning value and the signature class so the two resolutions never collide). 118/118 webcodium tests passing, 117/117 charter, manager suite unaffected by this phase (Phase A's `fetchViewCompositions` tests live in `manager/src/resolve/export-shape.test.ts`).
